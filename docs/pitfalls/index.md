# 踩坑记录

> 报错不是失败，是游戏读档点。规矩：每条记录都要写全「现象 → 当时在干什么 → 原因（大白话）→ 怎么解决 → 学到什么」。报错原文尽量原样贴，将来搜索时能对上。

## #001 `'git' 不是内部或外部命令`

- **现象**：在 cmd 里敲 `git --version`，返回：

  ```txt
  'git' 不是内部或外部命令，也不是可运行的程序或批处理文件。
  ```

- **当时在干什么**：检查电脑环境，确认 Git 装没装。
- **原因（大白话）**：cmd 接到一个命令名后，会按 **PATH**（环境变量里的「地址簿」）挨个文件夹找同名程序；地址簿里没有 git 所在的文件夹，就报这条错。**这条错只说明「找不到」，不代表「没装」**——当时 git 其实就躺在另一个项目的 `_tools\cmd` 里，只是那个文件夹不在地址簿上。
- **怎么解决**：要么把程序所在文件夹加进 PATH，要么像我一样直接用完整路径调用（`"C:\...\_tools\cmd\git.exe" --version`）。
- **学到什么**：见到「不是内部或外部命令」，第一反应应该是「查地址簿」，而不是「软件坏了」。详见[前置知识 01 · 命令行](/prereq/01-command-line)。

## #002 Git 明明没装，`.gitconfig` 却存在

- **现象**：`git` 命令跑不了，但 `C:\Users\王奕博\.gitconfig` 文件实实在在存在，里面还写着 GitHub 用户名。
- **当时在干什么**：环境检查时发现 Git 报「找不到」，顺手查了用户主目录。
- **原因（大白话）**：`.gitconfig` 是 Git 的**配置文件**，程序和配置是两回事——之前的会话用便携版 Git 干过活、写过配置，后来环境变量里找不到程序了，配置文件却留了下来。就像搬走了钢琴，琴谱还留在墙上。
- **怎么解决**：不用删。找到（或重新装）Git 后，这些配置（用户名、邮箱、凭据助手）自动生效。
- **学到什么**：报错说「程序找不到」≠「一切从零开始」。排查环境时，配置文件、安装目录、PATH 要分开看。

## #003 PowerShell 脚本里的中文路径变乱码

- **现象**：执行 `.ps1` 安装脚本，报「对路径『涓汉椤圭洰Wiki缃戠珯』的访问被拒绝」——好好一个「个人项目Wiki网站」变成了一串天书。
- **当时在干什么**：跑自动下载 Node.js 的 PowerShell 脚本，脚本里写死了中文路径。
- **原因（大白话）**：**编码问题**。Windows 自带的 PowerShell 5.1 读「无 BOM 的 UTF-8」脚本时，会按系统默认的 GBK 编码去解——中文每个字被错误拆分，全变乱码，路径自然不存在。
- **怎么解决**：脚本里**只用 ASCII 字符**：不写死中文路径，改用 `$PSScriptRoot`（脚本自己所在的文件夹）来定位；或者保存成「带 BOM 的 UTF-8」。
- **学到什么**：写自动化脚本，路径、文件名尽量用英文；中文不是不能用，但要理解编码这层「翻译」。这也是为什么项目文件夹最好起英文名。

## #004 GitHub 的 token 权限不够（缺 workflow scope）

- **现象**：用 gh CLI 登录 GitHub 没问题，但把 `.github/workflows/deploy.yml` 推上去时会被拒绝（ refusing to allow ... create or update workflow）。
- **当时在干什么**：首次推送仓库，其中包含自动部署的工作流文件。
- **原因（大白话）**：GitHub 的 **token**（令牌）像一张**门禁卡**，每张卡上刻着能开哪些门（叫 **scope**，权限范围）。当时的卡有 `repo`（读写仓库）权限，但没有 `workflow`（创建/修改自动化工作流）权限——这是防止偷卡的人偷偷改你的自动化流水线。
- **怎么解决**：给卡加权限：`gh auth refresh -s workflow`，它会给你一个一次性代码，去浏览器 `github.com/login/device` 输入并授权即可（浏览器里已登录 GitHub 的话就是点两下）。
- **学到什么**：token = 门禁卡，scope = 卡上刻的门。权限报错先看「卡上刻了什么」，而不是急着重新登录。

## #005 国内网络装依赖慢/失败 → 用镜像

- **现象**：`npm install` / `pip install` 龟速甚至超时断开。
- **当时在干什么**：安装 VitePress 依赖、下载 Node.js 安装包。
- **原因（大白话）**：官方仓库的服务器大多在国外，链路又远又挤。
- **怎么解决**：换国内**镜像**（官方仓库的国内分店）：
  - npm：本项目已配 `.npmrc` 指向 `https://registry.npmmirror.com/`
  - pip：`py -m pip install 包名 -i https://pypi.tuna.tsinghua.edu.cn/simple`
  - Node.js 安装包：`https://registry.npmmirror.com/-/binary/node/`
- **学到什么**：下载慢先想「哪里有分店」，别傻等。详见[前置知识 02](/prereq/02-node-and-npm) 与 [06](/prereq/06-python-env)。

## #007 Node v22.0.0 的 V8 崩溃 bug

- **现象**：`vitepress build` 启动约 0.6 秒即崩：`FATAL ERROR: NewSpace::EnsureCurrentCapacity Allocation failed - JavaScript heap out of memory`（堆才用了几 MB 就"溢出"，明显不正常）。
- **当时在干什么**：开启 `lastUpdated: true` 后重新构建站点。之前同一版本构建成功过，纯属没踩到触发路径。
- **原因（大白话）**：Node.js v22.0.0 这个「大版本第一版」自带一个 V8 引擎的回归 bug，特定 GC 路径必崩，22.1.0 就修了。教训：**装运行时永远别装 x.0.0**，等至少一两个补丁版。
- **怎么解决**：升级便携 Node 到 v22.14.0（`_tools\upgrade-node.ps1` 一键换新）。
- **学到什么**：遇到「不可能这么快就堆溢出」的崩溃，先查运行时版本的已知 bug，别急着怀疑自己代码。

## #006（预防篇）部署后整站白屏/样式全丢

- **现象**：本地预览一切正常，部署到 GitHub Pages 后打开是白屏，浏览器控制台一堆 404。
- **为什么提前记**：这是 VitePress + GitHub Pages 的**经典第一坑**，本站配置时已提前规避，记下来防将来复发。
- **原因（大白话）**：GitHub Pages 把站点挂在 `https://用户名.github.io/my-wiki/` 这种**子路径**下，而 VitePress 默认按「根路径」生成链接（比如去找 `/assets/xxx.js`），实际上文件在 `/my-wiki/assets/xxx.js`——所有资源都 404，样式脚本全加载不到。
- **怎么解决**：在 `docs/.vitepress/config.mjs` 里写 `base: '/my-wiki/'`（仓库名是什么就写什么）。本站配置里那一行就是干这个的。
- **学到什么**：「本地好的，线上一塌糊涂」先想路径差异：根路径 vs 子路径。
